# Reframing What Psilia Is

> *We want to make prototyping for edge devices as easy as prototyping on your local machine.*

Robotics teams duct-tape these things on the fly.
They don't ask what the experience should have been.
Best practices go under when deployment pressure is on.
How many teams set up benchmarks and build infrastructure
tooling when they are in a sprint to hit a milestone?

At the core of every robotics prototype is a perception stack.
Getting it running is where the first wall is.
Psilia provides the perception runtime. It does two things:
setting up perception delivers immediate value, and
owning setup installs the hooks into the device that enable
the full prototyping experience downstream.

The runtime is also the first thing that touches raw sensor data,
making it the natural entry point for a data flywheel:
every team running Psilia generates signal about
real-world failure modes, environments, and edge cases
that compounds over time.

From the data flywheel we can go in two directions: improving core
perception algorithms and leaning into the edge-native angle, or
going deeper into the prototyping cycle:
benchmarking, testing, helping teams improve
their own algorithms, and redeployment.

This actually suggests two different companies, different in spirit
but not in starting point. Both start with the runtime,
as a wedge and a hook into the device.

The developer tools company invests in workflow, data platform, and tooling,
growing with the teams that depend on it.
The perception company uses it as a wedge into the data,
investing in algorithms, benchmarks, and edge-native research,
with the data flywheel feeding the algorithmic core.
